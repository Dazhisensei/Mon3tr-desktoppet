# 桌宠项目（DesktopPet）

Windows 桌面宠物，基于 Tauri 2 + Rust + WebView2。

## 操作

| 操作 | 效果 |
|---|---|
| 拖动角色 | 移动窗口位置（会暂停自主行为几秒）|
| 单击角色 | 播放「点击」特效，播完自动回到待机 |
| 右键 | 打开菜单 |

窗口位置与缩放会自动保存，下次启动回到原位。

## 自主行为

桌宠大部分时间处于待机，会随机触发休息与行走（参数在 `web/brain.js` 的
`BEHAVIOR` 中，改这些数就能调节「性格」）。

实测比例（30 分钟仿真，1920×1080）：

| 状态 | 占比 |
|---|---|
| 待机 | ~65% |
| 休息 | ~19% |
| 行走 | ~16% |

> 上表为**加入休息门槛前**的旧数据。现在休息只在安静 10 分钟后才可能
> 触发，实际操作时占比会明显更低。可用 `_work/sim.mjs` 重新测量。

**行走规则：**

- 起步时如果已经靠近屏幕某一侧（左右各 25% 区域内），就朝**另一侧**走
- 行走中碰到屏幕边缘会掉头
- 有 25% 概率为「长途行走」：一直走到边缘才转向，形成巡逻感
- 窗口始终被约束在屏幕工作区内，不会越界

行为参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `idleMin` / `idleMax` | 4~12 秒 | 待机持续时长 |
| `restMin` / `restMax` | 5~15 秒 | 休息持续时长 |
| `walkMin` / `walkMax` | 3~9 秒 | 普通行走时长 |
| `pIdleAgain` | 0.45 | 待机后继续待机的概率 |
| `pRest` | 0.45 | 决定行动时选休息的概率 |
| `pLongWalk` | 0.25 | 长途行走概率 |
| `walkSpeed` | 60 px/s | 行走速度 |
| `followSpeed` | 130 px/s | 跟随鼠标的基准速度 |
| `followSpeedGain` | 1.0 | 跟随的距离增益（越远越快）|
| `followSpeedMax` | 320 px/s | 跟随速度上限 |
| `followDeadZone` | 0.06 | 跟随死区（避免中心抖动）|
| `edgeZone` | 0.25 | 触发「朝反向走」的边缘区域比例 |
| `restIdleMs` | 600000 | 触发休息所需的无操作时长（10 分钟）|
| `dragHold` | 2500 ms | 拖拽后暂停自主行为的时长 |

## 动画流畅性处理

动作切换容易出现两类观感问题，本项目都做了处理：

**1. 切换闪烁**

原因：切换动作时旧帧已清空、新帧尚未绘制，中间出现空白。

处理（`main.js` 的 `setAction`）：

- 全部帧解码完成后才替换显示，杜绝「半成品」状态
- 递增 token 做并发保护，连续快速切换时只有最后一次生效
- 替换后**立即绘制一帧**，不留间隙

**2. 过渡生硬**

原因：两个动作的姿态不同，硬切会「跳」一下。

处理：

- **交叉淡化**：切换时把上一帧以衰减不透明度叠加在新帧上（180ms，缓出曲线），
  过渡是「融」过去而不是「跳」过去

> **关于「循环对齐」的取舍**
>
> 曾尝试过「等当前循环播完再切换」，让衔接点落在相同姿态上。
> 但这要求显示层与行为层保持状态同步，实测会出现两者失配、
> 动画彻底卡死的问题（30 次运行中约 2 次触发）。
>
> 现在改为**立即切换**，完全依靠交叉淡化掩盖姿态差异。
> 显示层永远紧跟行为层，不存在状态不一致的可能，可靠性优先。

**3. 点击后静止**

原因：单击时调用 `holdUser()` 暂停自主行为，动画播完后仍处于暂停期，
导致约 1.8 秒的静止空档。

处理：`playOneshot()` 会清除暂停标记，点击动画播完立刻接上待机。
实测空档从 ~1800ms 降到 **87ms**。

**4. 启动时乱切动作**

`Brain` 的 `until` 初值为 0，主循环首帧即满足 `now >= until`，
会立刻触发一次行为决策。因此 `boot()` 结尾必须显式调用
`brain.enterIdle()` 让行为正式起步。

**5. 手动切动作导致永久卡死**

早期实现里，菜单手动选动作会设置 `brain.pausedByUser = true`，
而 `tick()` 开头就是 `if (this.pausedByUser) return;`——
**状态机从此完全停止**，表现为：

- 点击特效播完卡在最后一帧，回不到待机
- 手动切到行走后一直走，停不下来

修复：改为**临时接管**机制。手动选动作后只接管 `MANUAL_HOLD_MS`
（6 秒），到期自动 `enterIdle()` 恢复自主行为。
接管期间跳过 `tick`，但**一次性动作例外**（否则点击特效播完无法回待机）。

**6. 行走原地踏步（DPI 缩放）**

本机 DPI 缩放为 125%。窗口尺寸用 `LogicalSize`（逻辑像素），
而 `get_screen_info` 返回与 `set_position` 使用物理像素，
两者混用导致每帧位移在换算中相互抵消，表现为原地踏步。

修复：

- `set_scale` 改用 `PhysicalSize`，并按 `scale_factor` 换算
- 行走期间不用后端返回值覆盖本地推算的窗口位置
  （`move_window` 是异步的，取回的可能是上一次的位置）
- 只更新屏幕边界，位置以本地推进为准

**7. 画面出现「双影 / 第一帧叠加」**

早期为了实现柔和过渡，切换动作时把上一帧按不透明度叠在新帧上。
但这对**逐帧动画是有害的**：两帧的角色姿态不同，叠加会产生双影，
观感上就是画面上同时出现两个角色轮廓。频繁切换时尤其明显。

修复：**移除交叉淡化**，只绘制单帧。过渡的观感由「不延迟切换 +
帧率稳定」来保证，而不是靠混合两帧。

**8. 连续切换后画面永久卡死**

`setAction` 曾用 token 做并发保护：

```js
const myToken = ++switchToken;
const imgs = await loadFrames(key);
if (myToken !== switchToken) return;   // ← 问题所在
```

一旦某个请求被后来的请求「覆盖」，它就直接 return，**连
`state.current` 都不更新**。若后续又有同动作请求，
`if (state.current === key) return;` 会立即短路——
结果是所有请求都被丢弃，画面永久停在旧帧。

修复：**启动时预载全部动作帧**，切换变为同步替换，不存在 await
窗口，竞态从根本上消失。

**9. 放置一会后动画卡死 / 菜单操作后卡死**

根因是 `brain.paused` 这个标志：菜单打开时置 `true`，
只有点到菜单外部（`hideMenu`）才会复位。一旦菜单没有正常关闭
（切换窗口、失焦、点了菜单项但在异步流程中提前返回等），
`paused` 就**永久为 true**，`tick()` 开头直接 return，
状态机静默死掉。

修复：**删除所有「永久暂停」标志**（`paused` 与 `pausedByUser` 全部移除）。
现在只剩 `holdUntil` 一个暂停机制，它是**基于时间戳的，必然自动过期**，
不存在永久卡死的可能。

菜单打开**不再暂停状态机**——菜单是瞬时交互，让它盖在动画上即可。

「暂停自主活动」改用 `manualHoldUntil = Infinity` 实现，
仍复用同一条路径，保证「恢复」一定能解开。

**10. 行走原地踏步（跨两轮才定位）**

前两轮分别改了像素单位和回读时机，都没解决。真正原因是
**整条链路的坐标系不一致**：

| 环节 | 原用坐标 |
|---|---|
| 鼠标 `screenX/Y` | 逻辑（CSS 像素）|
| `outer_position()` | 物理 |
| `move_window` | 物理 |
| `get_screen_info` | 物理 |
| `set_scale` | 逻辑 |

在 125% 缩放下这些值相差 1.25 倍，换算相互抵消，位移被吃掉。

修复：**全链路统一为逻辑坐标**。

- `get_screen_info` 按 `scale_factor` 换算后返回
- `move_window` 用 `LogicalPosition`
- `drag_start` 记录窗口位置时换算为逻辑值（原来与鼠标逻辑坐标直接相减，是 bug）
- `set_scale` 用 `LogicalSize`

**11. 放置一会后动画冻结（真正的根因）**

前面几轮都在状态机里找原因，方向错了。真正的根因在 **WebView2 的
后台挂起**：

> Tauri 的 `background_throttling` 默认策略是 `Suspend` ——
> 「不在窗口中的 webview 会完全挂起任务」。

桌宠窗口**从不获得焦点**，Chromium 据此判定它「被遮挡 / 不可见」，
于是**挂起整个 webview 的渲染任务**，`requestAnimationFrame` 完全停止。

这一个原因同时解释了几个看似无关的现象：

| 现象 | 解释 |
|---|---|
| 放置一会后卡死 | rAF 被挂起 |
| 右键切换只显示第一帧 | `setAction` 同步画了第 0 帧，之后循环不再推进 |
| 行走原地踏步 | `brain.tick` 不再被调用，窗口不移动 |
| 点击动画播不完、卡住 | 一次性动作的结束判定依赖循环推进 |

修复分三层：

1. **Rust 侧**：设置 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`
   禁用 Chromium 的后台与遮挡挂起：

   ```
   --disable-background-timer-throttling
   --disable-backgrounding-occluded-windows
   --disable-renderer-backgrounding
   --disable-features=CalculateNativeWinOcclusion
   ```

   注意：Tauri 的 `background_throttling` 配置**在 Windows 上不生效**
   （官方文档标注 `Linux / Windows / Android: Unsupported`），
   只能用启动参数。

2. **主循环健壮化**：`requestAnimationFrame(frame)` 改为**无条件调度**，
   主体用 `try/catch` 包住。早期把它放在函数末尾，一旦抛异常循环就
   永久停止。

3. **看门狗**：`setInterval` 每 100ms 检查，若超过 400ms 没有推进
   就接管驱动。即使 rAF 被挂起，桌宠仍在动。

**12. 右键选「行走」原地踏步（第二个独立原因）**

除了上面的挂起问题，这里还有一个**独立**的设计错误：

```js
if (!manualHoldUntil || brain?.state === 'oneshot') {
  brain?.tick(now, dt);   // 手动接管期间完全跳过
}
```

手动选「行走」后 `manualHoldUntil` 生效，`brain.tick` 被**完全跳过**，
窗口根本不会移动——只是播放了行走动画，所以看起来是原地踏步。

修复：**手动选动作时直接进入对应的行为状态**，不再冻结状态机。

- 选「行走」→ `brain.enterWalk()` 并给较长时长 → 真的会走
- 选「休息」→ `brain.enterRest()`
- 选「待机」→ `brain.enterIdle()`
- 选「点击」→ `brain.playOneshot()`

`manualHoldUntil` 机制整个移除，只保留用户显式切换的「暂停自主活动」。

**13. 「行走」按钮完全无反应（真正的根因）**

一个**漏赋值**导致的功能整体失效：

```js
constructor({ onAction, onMove, onTurn, getScreen }) {
  this.onAction = onAction;
  this.onMove = onMove;
  this.onTurn = onTurn;
  // ← 漏了 this.getScreen = getScreen;
}
```

`pickDirection()` 与 `stepWalk()` 都依赖 `this.getScreen()`，
于是 `enterWalk()` 一调用就抛 `TypeError`，
**在 `onAction('move')` 之前中断**。

这一个 bug 同时解释了之前所有「行走」相关的怪现象：

| 现象 | 原因 |
|---|---|
| 菜单「行走」像死按钮 | `enterWalk` 抛异常，点击处理器中断 |
| 行走原地踏步 | 异常发生在切换动画之前，状态从未进入 WALK |
| 自动行走从不发生 | 同上 |

修复：

1. 补上 `this.getScreen = getScreen;`
2. **所有回调都给出安全默认值**，缺哪个只会让对应功能降级，
   不会连带崩掉其他功能：

   ```js
   const fn = (f, fallback) => (typeof f === 'function' ? f : fallback);
   this.getScreen = fn(getScreen, () => null);
   ```

**为什么之前的仿真没发现它？**

因为仿真脚本**自己重写了 `Brain` 类**（`getScreen` 写成了方法），
恰好写对了，于是测的是「我以为的代码」而不是「实际代码」。

**这是本项目最重要的排查教训**：仿真/测试必须**加载真实源码**，
不能手写一份"等价"实现——否则它会掩盖真实代码里的低级错误。
`_work/sim_fixes.mjs` 已改为加载真实的 `brain.js` 与 `main.js`。

**14. 点击特效到待机的过渡过快**

点击动画播完后立即切回待机，观感上像「刚放完特效就急着切走」。

点击动画的首尾姿态一致（都是自然站姿），所以末尾会停在站姿上，
只需在切走前多停一会儿即可。

`main.js` 中集中为一个常量（两处调用共用，避免改漏）：

```js
const CLICK_HOLD_MS = 420;   // 原为 80ms
```

实测停顿由 **87ms 延长到 423ms**。想再调节奏直接改这个值。

**16. 缩小比例时只有窗口在缩、桌宠头部被截断**

现象：在设置里把尺寸调小后，**透明窗口变小了，但角色没跟着缩**，
超出的上半身被窗口边缘切掉，看起来像「头没了」。

根因是 **`userScale` 与窗口尺寸不同步**，触发链路：

1. 打开设置面板 → 窗口临时放大到 440×560
2. 拖动尺寸滑条 → 调用 `set_scale`，但 Rust 走**延迟分支**
   （面板占着窗口，不能立刻改尺寸），**只写配置、不广播事件**
3. 关闭面板 → `exit_settings_ui` 把窗口按新缩放改小，
   但**没有补发** `settings:scale`
4. 前端 `userScale` 仍停在旧值 → 画布按旧的大尺寸绘制

而画布容器 `#stageWrap` 是 `bottom: 0` 锚定的，
比窗口高的部分**只会从上方溢出**被裁掉 —— 正好切掉头部。

实测（45% 缩到 20%）：

| | 窗口 | 画布 | 角色头顶 |
|---|---|---|---|
| 修复前 | 181×141 | 407×317 | y = **-121**（在窗口外）|
| 修复后 | 181×141 | 182×142 | y = **+23.6**（正常）|

修复分三层，从治本到兜底：

1. **`exit_settings_ui` 补发 `settings:scale`**（治本）
   放在 `set_size` **之后**发，确保前端收到时窗口尺寸已是最终值。
2. **`fitStage` 按窗口尺寸夹取**
   `scale = min(userScale, fitW, fitH)` —— 正常档位下 min 就是
   `userScale`，行为不变；一旦失配画布立刻收缩进窗口。
3. **`syncScaleFromWindow` 自愈**：`resize` 与关闭面板时按窗口反推
   修正 `userScale`。只在**宽高同时吻合**且落在 20%~100% 内才采纳，
   因此气泡扩窗（只改宽度）、设置面板尺寸（440×560 非素材比例）
   都不会被误判。

> **教训**：「延迟应用」的配置项必须在**真正生效的那一刻**补发通知，
> 否则前端会一直停在旧值。仅靠前端自愈是不够的 ——
> 两条路都要有，一条保证正确、一条保证不出事。

**教训**

这个项目反复踩的坑，归纳为八条：

1. **回调赋值要完整，且给默认值**。漏一个 `this.x = x` 就能让一个功能
   静默失效，而现象只是「按钮没反应」。
2. **不要有「永久暂停」标志**。暂停必须基于时间戳、自动过期。
3. **坐标系必须全链路统一**。逻辑/物理像素混用在 100% 缩放下正常，125% 就错位。
4. **异步调用的返回值不能当作「当前状态」**。
5. **不要用「混合两帧」给逐帧动画做过渡**，会产生双影。
6. **菜单等瞬时交互不应冻结主循环**。
7. **渲染循环要假定「随时可能被挂起」**：无条件重新调度 + 看门狗兜底。
   桌面宠物这类「长期运行、永不聚焦」的窗口尤其容易触发浏览器后台节流。
8. **「延迟应用」的配置必须补发通知**。否则前端一直停在旧值，
   而现象是「窗口变了、画面没变」这类看似无关的错位。

### 排查这类问题的方法

「动画卡住」是笼统现象，对应完全不同的原因。有效的判据：

| 观察 | 指向 | 该查什么 |
|---|---|---|
| 只显示第一帧 | **循环停止** | rAF 调度、后台挂起、异常中断 |
| 动画在播但窗口不动 | **行为层没被调用** | 调用条件、回调是否赋值 |
| 按钮无任何反应 | **处理器中途抛异常** | 从入口逐层 try/catch 或打印堆栈 |

配套手段：

- **静态检查优于猜测**：用脚本 grep 源码确认结构性约束
  （如「无永久暂停标志」「回调都已赋值」）。
- **仿真必须加载真实源码**：手写等价实现会掩盖真实缺陷。
- **在 Node 里桩化 DOM**，直接驱动真实的 `main.js` 并按事件点击，

**15. 设置里改语言/点试听毫无反应（ACL 权限缺失）**

**现象**：设置里切成「日本語」后仍播中文；「试听」按钮完全没反应。

**根因**：项目**没有 `capabilities` 目录**，而 Tauri 2 的事件系统
（`core:event:allow-listen`）是**受 ACL 保护**的。生成的
`build/.../out/capabilities.json` 是一个**空对象 `{}`**，
于是前端所有 `listen()` 调用都被拒绝：

```
Command core:event|listen not allowed by ACL
```

`main.js` 的 `safe()` 只写了 `console.error`，而桌宠没有 DevTools
—— 故障完全静默。**6 个设置项此前全部失效**：

| 事件 | 本应做什么 |
|---|---|
| `settings:voice-lang` | 切换语音语言 |
| `settings:preview-voice` | 试听 |
| `settings:volume` | 音量作用于播放中的语音 |
| `settings:passthrough` | 关掉点击穿透 |
| `settings:scale` | 改尺寸后刷新行走边界 |
| `settings:birthday` | 生日改动同步到本地 |

**为什么之前没发现**：`invoke()` 把所有异常 `console.warn` 后返回
`undefined`，调用方看到的是「什么都没发生」而不是报错。

**修复分三层**：

1. **补上 `src-tauri/capabilities/default.json`**，授予
   `core:event:default`（含 `allow-listen`）等权限，窗口限定 `pet`：

   ```json
   { "identifier": "default", "windows": ["pet"],
     "permissions": ["core:default", "core:event:default", ...] }
   ```

   注：**应用自身的命令不需要 ACL 条目**——它们由
   `generate_handler!` 直接注册。被拦的是 `core:event:listen`
   这类核心命令。

2. **增设直连通道**。设置面板与主窗口其实是**同一个窗口**，
   `settings:*` 事件只是早期「两个 webview」设计的历史包袱。
   现在 `initSettingsPanel` 额外接收 `onLangChange` /
   `onVolumeChange` / `onPreview` 三个回调，**直接调用**主窗口函数。
   事件与直连并行，任一可用即可生效。

3. **让失败可见**：监听失败现在会 `toast` 提示并把结果写入
   `window.__settingsEvents = { ok, failed }`，不再静默。

**教训**：涉及 IPC/权限的调用，**不能让 `catch` 静默**。
本项目已有 6 个功能因此悄悄失效而无人察觉。

## 天气

右键 →「天气」，桌宠会查询已设置的地区，用**对话气泡**报天气，并播对应语音。

### 数据源：Open-Meteo

选它的理由：

| 维度 | 情况 |
|---|---|
| API Key | **不需要** |
| 费用 | 非商业免费 |
| 请求数 | **多城市一次请求**（坐标逗号分隔）|
| 数据源 | 官方气象机构（含中国 CMA）|

**两段式调用**，日常开销极小：

1. **地理编码**（城市名 → 经纬度）：只在设置里添加城市时调 **1 次**，
   结果**存进配置**，之后不再调用
2. **取天气**：每次点「天气」发 **1 个请求**，同时带回全部城市，约 1–2 KB

天气码是 WMO 标准码，在 `weather.js` 里**本地映射**成中文（晴/多云/小雨…），
不额外发请求。

### 缓存

同一批城市 **1 小时内**重复查询直接用缓存，连点不会产生多余请求。
缓存键是城市坐标串，改城市列表自然失效。

### 气泡

**用 DOM + CSS 实现，不需要美术素材。**

角色素材是 906×704 的整幅画布，实测角色包围盒为 `x=160~584, y=144~660`
—— 顶部约 20% 是空白，正好容纳气泡。DOM 的好处是自动换行、随窗口缩放、
点击即收起，不必为每句话出图。

显示内容：

```
博士，这是今天的天气情况：        ← 第一行固定
北京 ☀️ 晴 16~26℃  体感19℃ 湿度45% 风10km/h
上海 ⛅ 多云 22~30℃  体感24℃ 湿度60% 风8km/h
```

窗口很小时（< 320px，即 25% 档）自动切换 `compact` 模式，
省略体感/湿度/风力，避免气泡撑爆。

### 失败处理

| 情况 | 气泡 | 语音 |
|---|---|---|
| 没设置地区 | 提示去设置，**不发请求** | 天气失败 |
| 联网失败/超时 | 博士…出了些问题，我查不到天气 | 天气失败 |
| 正常 | 天气列表 | 天气 |

请求有 **8 秒超时**（自己用 `AbortController` 实现）—— 网络不可达时
`fetch` 可能长时间挂起，界面会一直停在「查询中」。

### 与点击穿透的联动

气泡是 DOM 元素，**不参与画布的 alpha 采样**。若不特殊处理，会被判为
透明区域而穿透，既点不到也显得残缺。因此气泡显示期间强制关闭穿透
（与菜单/设置面板同一处理）。

### 所在地区设置

设置 →「所在地区」，最多 **3 个**。

输入城市名 → 搜索 → **从候选列表里点选确认**。必须让用户确认，因为
同名地点很多（如「朝阳」会返回朝阳区（北京市）与朝阳市（辽宁省））。

### 中文地名：为什么要「多次尝试」

Open-Meteo（底层是 GeoNames）的匹配规则有个坑：

> Two characters match an **exact** name. Three or more use **prefix** matching.
> …the characters must match the **beginning of an indexed name**.

两个问题叠加：

1. **2 个字符走精确匹配**（3 个以上才是前缀匹配）
2. 索引的主名多是**拼音**，中文名往往只是 alternate name

于是「滨州」这种**两个汉字**的普通地级市直接查不到——2 字符精确匹配，
主名又是 `Binzhou`，对不上。（「北京」因为另有独立条目才恰好能用。）

`searchCity` 因此按顺序尝试多种写法，任一有结果就返回：

| 顺序 | 尝试 | 说明 |
|---|---|---|
| 1 | **拼音**（`Binzhou`）| 实测命中更准，见下 |
| 2 | 原样 | 大多数情况够用 |
| 3 | 补省份（`滨州, 山东`）| 长度变 >= 3，改走前缀匹配 |

**为什么拼音排第一**：中文名匹配经常返回一堆同名小地方（村、镇、区），
而拼音对应的往往是 GeoNames 的**主条目**——人口更多、更可能是用户
想找的市。实测拼音比中文名更准。

结果还会**按相关性重排**（`rankResults`）：名称与查询一致的优先，
其次人口多的优先。这样真正想找的城市会冒到列表最上面。

省份对照表 `CN_PROVINCE_BY_CITY` 与拼音表 `CN_PINYIN` 内置在
`weather.js`，覆盖全国地级市。用户也可以自己写「城市, 省份」直接命中，
此时**不做任何改写**，原样查询。

> 这两张表是**离线**的，不产生额外请求。命中后不会继续尝试其他写法。

### 显示内容

每座城市 **3 行**（`compact` 时压成 1 行）：

```
博士，这是今天的天气情况：
北京 ☀️ 晴  16~26℃
体感19℃  湿度45%  东南风12km/h  降水概率10%
  建议：薄外套或针织衫；早晚较凉，备件外套；紫外线中等
```

- 第 1 行：城市 + 天气 + 今日温度区间
- 第 2 行：体感、湿度、风向风力、降水概率
- 第 3 行：生活提醒（缩进、绿色、左侧竖线）

取的数据：实况温度/体感/湿度/天气码/风速/风向/气压/降水量，
今日最高最低温/降水概率/紫外线/日出日落，另取**明日**温度备用。

### 生活提醒

按**重要程度排序**并限制最多 3 条——气泡空间有限，全塞进去会变成
一大段字反而没人看。优先级：

| 顺序 | 提醒 | 判据 |
|---|---|---|
| 1 | 带伞 / 路滑 | 天气码（雨、雪、雷暴）|
| 2 | 穿衣 | **体感温度**分 9 档 |
| 3 | 昼夜温差 | 温差 ≥ 9℃ 提醒增减衣物 |
| 4 | 紫外线 | UV ≥ 3 分级提醒防晒 |
| 5 | 干燥 / 潮湿 | 湿度 ≤ 35% 或 ≥ 70% |
| 6 | 风力 | 风速 ≥ 20 km/h |
| 7 | 气压偏低 | ≤ 995 hPa 容易疲倦 |

穿衣用**体感**而不是气温：同样 5℃，有风时体感接近 0℃，
只看气温会穿少。

### 气泡尺寸与「内容变少」的坑

气泡最初是 `max-width: 62%` + `white-space: nowrap` + `ellipsis`。
天气行有 35~40 个字符，而各档位气泡内宽分别只够显示约：

| 档位 | 窗口 | 气泡内宽 | 可显示 |
|---|---|---|---|
| 25% | 226px | 193px | ~17 字 |
| 35% | 317px | 280px | ~25 字 |
| 50% | 453px | 411px | ~37 字 |

除大窗口外，后半截都被**省略号截掉**，看起来就像"内容少了很多"，
只剩城市、温度与天气状况。

修复分三层：

1. **允许换行**：`white-space: normal`（信息完整优先于排版整齐）
2. **放大气泡**：宽度 62% → **96%**，高度上限 → 62vh
3. **小窗口单独放宽**：`@media (max-width: 340px)` 下宽度 99%、
   高度上限 **78vh**（25% 档窗口仅 176px 高，62vh 只有 109px，
   两三行就触发滚动，看起来又像"信息不全"）

同时**取消了 `compact` 丢数据的做法**：以前窄窗口会砍掉体感/湿度，
现在气泡能换行、也放得下，再丢就纯粹是"看着少了东西"。
小窗口只把生活提醒从 3 条压到 2 条，**数据始终完整**。

### 气泡的定位：固定顶部、固定高度、内部滚动

气泡**固定在窗口顶部往下铺，高度固定为窗口的 60%，内容超出就内部滚动**。
窗口尺寸**完全不变**。

```css
#bubble { top: 1.5%; height: 60%; overflow-y: auto; box-sizing: border-box; }
```

#### 为什么不是「贴角色头顶」

角色头顶以上的空白只占窗口高度的约 20%：

| 档位 | 窗口高 | 头顶以上 |
|---|---|---|
| 20% | 141px | **29px** |
| 25% | 176px | 36px |
| 35% | 246px | 50px |
| 50% | 352px | 72px |

20% 档只有 29px，**连一行都放不下**。贴头顶生长必然被窗口顶边截断。

#### 也试过「显示气泡时临时扩大窗口」，已放弃

那套方案理论上能解决空间问题，但要同时联动四件事，任何一处出错
都表现为**角色被截断**（实测反复踩坑）：

1. 窗口原点偏移（向上长 `dh` 必须 `y -= dh`，否则角色跟着跳）
2. 画布重新锚定与缩放（不能用窗口宽度反推，否则角色跟着变大）
3. 气泡定位不能用窗口高度百分比（扩窗会改变窗口高度，
   百分比算出的值跟着变，气泡被推离角色）
4. 穿透坐标换算（扩窗后窗口比画布大，直接乘会错位）

而且小尺寸下即使扩窗成功，窗口也可能顶到屏幕边缘而放不下。

**现在的做法简单且可预测**：窗口尺寸不动 → 角色永远不会被裁。
代价是小窗口下气泡会盖住角色头部，但这是**可预期**的 ——
读文字时本来就不需要同时看角色。

#### 保留的两处结构改动

这两处与气泡无关，属于独立的正确性问题，因此保留：

**画布分两层**（避免定位与翻转的 transform 互相覆盖）：

```
#stageWrap   定位：left:50% + bottom:0 + translateX(-50%)
└─ #stage    朝向翻转：scaleX(±1)
```

若两种变换都写在 canvas 的 `transform` 上，转身时会把居中也镜像掉，
角色会左右跳。

**画布缩放用 `userScale`**（用户设定值），而不是
`window.innerWidth / 906` 反推 —— 后者在窗口尺寸变化时会算出不同的
缩放，导致角色忽大忽小。画布尺寸 = 素材尺寸 × `userScale`。

#### 点击穿透与气泡

气泡是 DOM 元素，**不参与画布的 alpha 采样**。若不单独判断，
它会被当成透明区域而穿透，导致气泡点不动。
因此 `pollPassthrough` 里气泡显示期间强制关闭穿透
（与菜单、设置面板同一处理）。

## 随机关心

待机时每隔 **2–3 分钟**在气泡里说一句关心的话（素材 50 条，

### 为什么内置而不是运行时读 txt

随版本一起分发。

### 时段匹配

有些话天生属于特定时间——凌晨三点弹「早餐不要随便应付」很突兀。
因此给相关语句标上时段标签：

| 时段 | 小时 | 专属语句举例 |
|---|---|---|
| 早晨 | 5–9 | 起床、早餐 |
| 上午 | 9–11 | 早餐、睡眠基线 |
| 午间 | 11–14 | 午餐、午间小睡 |
| 下午 | 14–17 | 下午加餐 |
| 傍晚 | 17–19 | 下班走路、晚餐 |
| 晚间 | 19–23 | 晚餐七分饱、睡前准备 |
| 深夜 | 23–5 | 睡前泡脚、通宵提醒 |

规则：

- 通用语句（无标签）**任何时候**都可能出现
- 带标签的**只在匹配时段**进入候选
- 当前时段的专属语句**权重 ×3**，让「早餐」更可能出现在早上，
  但通用语句仍有机会——否则同一时段反复只有那两条会很单调
- 时间是**本地时间**，判定只看小时

### 什么时候会说

到点后会先判断，**任一不满足就跳过**（等下一轮）：

- 只在**待机/休息**时——行走中插话很突兀
- 菜单或设置面板打开时不打扰
- 气泡已被占用（如正在显示天气）时不抢占
- 用户显式「暂停自主活动」时不打扰

用户交互（单击/拖拽/开菜单）会**重置计时**，刚操作完不会马上被唠叨。
最近的 10 句会被记住，避免短期内重复。

## 自主行为的「休息」门槛

休息原先按 `pRest = 0.45` 无条件参与决策，导致触发过频。
现在加了**安静时长门槛**：

```js
// brain.js 的 decideNext
const quiet = now - this.lastUserAt;
const canRest = quiet >= BEHAVIOR.restIdleMs;   // 默认 10 分钟
if (canRest && r2 < BEHAVIOR.pRest) this.enterRest(now);
```

- `restIdleMs = 10 分钟`：需求是「大约每十分钟无任何操作才休息」
- 单击、拖拽、开菜单都会调用 `noteUserActivity()` 刷新计时
- 不满足门槛时**改为行走**，不会卡着不动

实测：刚操作过时休息概率 **0%**；安静 15 分钟后约 **23.5%**
（低于原先无条件的 45%）。

> 注意 `lastUserAt` 初值为 0 会让「启动瞬间」被误判为安静了很久，
> 因此 boot 结尾显式调用一次 `markUserActivity()` 把它设为启动时刻。

## 跟随鼠标

右键 →「跟随鼠标」，桌宠按光标的水平方向移动；按钮随即变成
**「取消跟随」**，再点一次回到普通状态。

- 光标在窗口中心**右侧**就往右走，左侧就往左走
- **指针离得远也会追**：`rel_x` 在窗口外时是 `<0` 或 `>1`，
  仍能判断方向。曾写成「不在窗口内就不动」，结果指针一远就
  **原地踏步**（窗口不动，动画还在播）
- **离得越远走得越快**：基准 130 px/s，按距离增益最多到 320 px/s，
  否则指针在屏幕另一头时要挪很久
- 有 **死区**（默认 6%）：光标接近中心时不动，否则会每帧翻转方向、
  看着发抖
- 与「坐」互斥——同时跟随即坐着没有意义
- 约束在工作区内，不会跑出屏幕
- **不受「暂停自主活动」影响**：那个开关管的是「桌宠自己乱走」，
  不该拦住用户的跟随指令
- **打开右键菜单不会打断跟随**（菜单期间只是暂停自主行为）

### 光标位置从哪来

复用点击穿透的轮询（`get_cursor_rel`，60ms 一次），**不额外发请求**。

这里有个容易踩的坑：穿透判定在跟随中、拖拽中、菜单打开时会**提前
return**。若把取光标写在那些 return 之后，这些情形下光标位置会一直
停在上一次的值，跟随就动不起来。因此轮询**开头无条件先取一次光标**。

跟随期间**强制关闭穿透**：窗口正朝光标移动，若此刻穿透，光标会落到
桌面上，跟随的输入源就断了。

## 坐

右键 →「坐下」，桌宠保持坐姿；按钮变成**「起身」**，再点一次恢复。

坐是**持续性状态**，和别的动作有几点不同：

| 行为 | 说明 |
|---|---|
| 不被自主行为打断 | `until = Infinity`，不会随机切到待机/行走/休息 |
| 点击仍有效 | 播「点击特效」+「戳一下」语音，**播完回到坐**而不是待机 |
| **打开菜单不会站起来** | 菜单只暂停自主行为，不强制切待机 |
| 天气、关心语句照常 | 它们只用气泡，与行为状态无关 |

**「播完回到坐」是怎么实现的**：用一个独立的 `sitting` 标志记住
「用户想坐着」，而不是只看 `state === 'sit'`。点击时状态会临时变成
`oneshot`，但标志仍在；`enterIdle()` 检查这个标志，决定回坐还是回待机。

### 坐姿的显示补偿

`sit.mov` 是后补的素材，**画得明显偏小且底部悬空**（实测：坐姿角色高
302px，待机高 518px；坐姿底部 y=494，待机脚底 y=662）。直接播会
「一坐下就缩小一大圈」。

因此在渲染层做补偿（`main.js` 的 `ACTION_DRAW`）：

```js
const ACTION_DRAW = {
  sit: { scale: 1.32, anchorBottom: true },
};
```

- `scale: 1.32` —— 坐姿/站姿身高比约 0.77，符合现实中坐比站矮的比例
- `anchorBottom` —— **以脚底为锚点缩放**，否则放大后会往上飘

> 这是**纯显示层**的补偿，不改帧数据、不影响行为逻辑。

**主画布与穿透采样必须用同一套绘制**：穿了「点击穿透」时，可点区域是
按画布 alpha 判断的。若采样画布漏掉这个缩放，坐着的角色就会出现
「点不到脚、却能点到旁边的空白」。因此抽出了公共的 `paintFrame()`，
两边共用 —— 这类不一致很难靠肉眼发现，但用起来会明显别扭。

素材 `sit.mov`（1500×1000 ProRes 带 alpha、101 帧、30fps）放在
`F:\SSV\m3\`，与其他动作**共用同一裁切框**——已实测其角色包围盒
完全落在裁切范围内，相对位置与其他动作一致。

## 关心语句的冷却与操作无关

关心每 2–3 分钟尝试一次，**计时不受用户操作影响**——无论是否点按
桌宠，到点都会尝试。

这样做是有意的：若在点击/拖拽时重置计时，频繁操作会让关心永远
不触发，等于被用户的操作"饿死"。

到点时若不满足条件（气泡被占用、菜单打开、正在行走），**跳过这一次**，
但计时照常继续——不会因为被跳过而把间隔拉长。

允许说话的状态：**待机 / 休息 / 坐 / 跟随**。
跟随期间也可以说——气泡是窗口内的 DOM 元素，窗口移动时它跟着一起移动，
两者不会错开。只有「行走」例外（桌宠自己在溜达，此时插话意义不大）。

> 注意「休息」的门槛（`restIdleMs`）**仍然**会被操作重置——
> 那是「不要在你刚操作完就休息」，与关心是两回事。
> 两者在代码里已分开：`markUserActivity()` 只管休息，
> 关心由独立的定时器驱动。

## 设置

设置**不是独立窗口**，而是主窗口内的一块覆盖面板。

打开时（右键 → 设置…）：

1. Rust 端 `enter_settings_ui` 记下当前窗口几何，把窗口临时放大到 440×560
2. 面板铺满窗口显示，桌宠画面隐藏
3. 关闭时 `exit_settings_ui` 还原窗口尺寸与位置

| 分组 | 项 |
|---|---|
| 窗口 | 总在最前、点击穿透、尺寸滑条 20%~100%（整数百分比）、移到屏幕底部 |
| 声音 | 音量滑块、语音语言（中文 / 日本語）、生日（月/日）、试听 |
| 所在地区 | 天气城市，最多 3 个（搜索后从候选里点选）|

按 `Esc` 或点「关闭」退出。面板打开期间会**挂起点击穿透**并暂停自主行为。

### 为什么不用独立窗口

最初用的是独立设置窗口（`WebviewWindowBuilder`），但 WebView2 对
**同一用户数据目录下创建多个 webview 环境**很敏感，两次尝试都有问题：

| 尝试 | 结果 |
|---|---|
| 不指定 `data_directory` | 创建失败：`os error 5`（退回不可写的 `%LOCALAPPDATA%`）|
| 指定与其他窗口相同的 `data_directory` | 出现**空白且无法关闭**的僵尸窗口 |

参考 wry 的文档注释：

> **Windows**: Webview instances with different
> `CoreWebView2EnvironmentOptions` must have different `data_directory`s

即：共用同一用户数据目录的 webview，其环境选项必须一致，否则创建失败。
在「无焦点、常驻、由点击穿透动态管控」的桌宠窗口上，这条链路始终不稳定。

**改为复用主窗口后**，完全不涉及第二次 webview 创建——
而主窗口的渲染链路早已验证可用，因此这条路的可靠性高得多。

### 缩放的处理

面板占用窗口期间**不能直接改窗口尺寸**（面板会被裁切），
因此 `set_scale` 在面板打开时只写入配置、延迟生效，
等关闭面板时由 `exit_settings_ui` 按最新缩放还原。

## 菜单为什么用 DOM 而不是原生

菜单是**网页内的 DOM 菜单**。

```
互动      交谈 / 天气 / 跟随        ← 占位
          设置…                    → 打开设置窗口
动作      待机 / 行走 / 休息 / 点击特效
          随机行为一次 / 暂停·恢复自主活动
退出
```

### 打开菜单时会暂停行走

DOM 菜单在窗口内，**会跟着桌宠一起移动**——这是它的固有缺点。
规避方式是打开菜单时：

- **暂停自主行为**（桌宠不再走动，菜单自然不会「跑掉」）
- **同时切到待机**，让姿态稳定、观感清楚

关闭菜单后恢复打开前的状态（若用户原本就处于「暂停自主活动」，则保持暂停）。

菜单还限制最大高度并支持滚动：窗口较小时（25% 档仅 226×176），
菜单项多了会被裁掉、点不到。

### 为什么没采用原生菜单

原生菜单的好处是「不随窗口移动、不受窗口尺寸限制」，
看起来很合适，但两条路都走不通（均已实测）：

**尝试 1：Tauri 的 `menu.popup()`**

- **阻塞主线程**：Windows 下调用 Win32 `TrackPopupMenu`（同步阻塞），
  且 `popup_inner` 外层用 `run_item_main_thread!` 宏做 `rx.recv()`
  同步等待。于是事件循环冻住：桌宠不走、设置窗口打不开，
  菜单关闭后积压的移动指令一次性执行（「瞬移」）。
- **菜单事件不派发**：内部用 `TPM_RETURNCMD`，该标志让
  `TrackPopupMenu` 直接返回选中项而不发送 `WM_COMMAND`，
  而菜单事件正是靠 `WM_COMMAND` 派发的，因此 `on_menu_event`
  收不到事件（菜单项无反应）。

**尝试 2：自建 Win32 弹出菜单（后台线程 + `TPM_RETURNCMD`）**

理论上能同时解决上面两点（主线程不阻塞 + 自己拿返回值），
菜单也能弹出，但实测**菜单不出现**。最可能的原因：
`SetForegroundWindow` 在后台线程调用无效，而 Windows 要求弹出菜单的
宿主窗口是前台窗口，否则 `TrackPopupMenu` 立即返回 0（被取消）。

考虑到桌宠窗口是「无焦点、常驻、由点击穿透动态管控」的特殊窗口，
原生菜单在这套环境下稳定性不足，投入产出比低，最终选择 DOM 菜单
+ 打开时暂停移动。

## 点击穿透

窗口按「点击」特效的最大范围设定（906×704），而平时待机时角色只占中间
一块，四周大片透明区域会**挡住桌面图标**。

处理：轮询光标位置，采样该点像素的 alpha——

- 落在**透明处** → 开启穿透，点击落到桌面
- 落在**角色上** → 关闭穿透，角色可点
- 光标在**窗口外** → 穿透
- **拖拽中 / 菜单或设置面板打开** → 强制不穿透（否则会打断操作）

**为什么必须由原生侧提供光标位置**：一旦开启穿透，webview 就收不到
`mousemove`，前端无法自行得知光标何时回到角色上。因此由 Rust 的
`get_cursor_rel` 返回光标相对窗口的归一化坐标，前端用离屏画布采样 alpha。

轮询间隔 60ms，开销很低（只在帧变化时才重绘采样画布）。
默认开启，可在设置里关闭。

## 关键实现说明

### 为什么 WebView2 数据目录要显式指定

原版 Tauri 默认把 WebView2 用户数据放在 `%LOCALAPPDATA%\<应用标识>`。
该路径在部分环境下不可写，会导致窗口创建失败：

```
Failed to setup app: 拒绝访问。(os error 5)
```

因此 `lib.rs` 中改为手动建窗，并用 `.data_directory()` 指定到
**exe 同目录的 `webview-data\`**。这是本项目能正常启动的关键。

### 日志

运行日志写在 **exe 同目录的 `pet.log`**，包含启动、建窗、panic 等信息，
便于排查闪退类问题。

### 配置文件

`pet-config.json`（exe 同目录）保存窗口位置与缩放：

```json
{ "x": 100, "y": 100, "scale": 0.35, "always_on_top": true }
```

它监听 `127.0.0.1:8901`，通过上游代理访问 crates 索引。
`src-tauri/.cargo/config.toml` 已配置指向该中继。

### 完全离线构建（无网络出口时）

依赖已全部解压在 `_work/rust/cargo/registry/src/` 下，可以直接当
**目录源**使用，不需要索引、不需要中继：

```powershell
cargo build --offline --config _work\cargo-offline.toml `
  --manifest-path desktop-pet\src-tauri\Cargo.toml
```

配套脚本 `_work/make_checksums.py` 会从 `.crate` 归档补出 cargo 在
vendored 模式下必需的 `.cargo-checksum.json`（registry 的解压目录里
本身不含该文件，缺了会报
`failed to load checksum .cargo-checksum.json`）。

> 每拉取过新依赖后都要重跑一次 `make_checksums.py`，
> 否则新 crate 缺校验文件会导致离线构建失败。

## 打包

### 产物

| 文件 | 说明 |
|---|---|
| `dist\DesktopPet_0.1.0_x64-setup.exe` | **NSIS 安装程序**（推荐分发）|
| `dist\DesktopPet-0.1.0-win64.zip` | 免安装绿色版（解压即用）|

### 一条命令构建安装程序

```powershell
powershell -ExecutionPolicy Bypass -File _work\build_installer.ps1
```

脚本会自动设置 Rust 环境、检查 NSIS、离线编译、把产物复制到 `dist\`。

### 关键配置：`useLocalToolsDir`

`tauri.conf.json` 里设了：

```json
"bundle": { "useLocalToolsDir": true }
```

**这一项是必需的**。Tauri 默认把 NSIS 工具放在
`%LOCALAPPDATA%\tauri\NSIS`，而该路径在受限环境下**不可写**
（`WinError 5 拒绝访问`），会导致下载解包失败。

开启后 tauri-bundler 改用 `cargo metadata` 的 **target 目录**：

```
desktop-pet\src-tauri\target\.tauri\NSIS\
```

注意**不含 profile 层级**（不是 `target\release\.tauri`）——
放错层级会被忽略，Tauri 转而尝试联网下载。

### NSIS 版本必须匹配

Tauri 会校验 NSIS 的 SHA1，版本不符会重新下载（无网络则失败）。
当前 `tauri-bundler 2.10.1` 要求：

| 项 | 值 |
|---|---|
| NSIS | `nsis-3.11.zip` |
| SHA1 | `EF7FF767E5CBD9EDD22ADD3A32C9B8F4500BB10D` |
| 必需文件 | `makensis.exe`、`Bin/makensis.exe`、`Plugins\x86-unicode\additional\nsis_tauri_utils.dll` |

`_work/fetch_nsis.py` 会按这些常量下载并**校验 SHA1**，
放到正确位置（`upstream 代理需在 127.0.0.1:7897`）。

### 布局说明：资源已内嵌

`frontendDist: ../web` 会把整个前端（含 68 MB 的 PNG 序列与
3.4 MB 语音）**打进 exe**，因此：

- 绿色版**只需一个 exe**，无需附带 `web/` 目录
- exe 体积约 74 MB，属正常

程序运行时在 **exe 同目录**生成 `pet-config.json` 与 `webview-data\`，
所以**必须放在可写位置**（不要放 `C:\Program Files\`）——
绿色版的使用说明里已明确写出这一点。
